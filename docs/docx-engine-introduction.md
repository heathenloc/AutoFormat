# AutoFormat 编辑核心模块介绍

> 2026-10-04 更新：当前编辑核心已覆盖 35 个注册的类型化格式属性，并接入来源重放与首次 V1 自动编辑。完整能力、验收和限制见 [编辑核心初版](docx-engine-core-v1.md)。以下保留 2026-10-03 的对齐原型阶段介绍，不能用其“仅支持对齐”的状态描述当前实现。

> 依据当前项目架构与实现整理，日期：2026-10-03。下文区分已实现能力与后续建设目标。

AutoFormat 的编辑核心负责把经过校验的格式规则落实到论文 DOCX，并验证修改结果。它接收选定的论文版本、明确的目标对象、格式属性、目标值和作用范围，通过确定性程序修改文档副本，再输出新的 DOCX 和逐项执行结果。Brief Parsing 负责理解学校要求，编辑核心负责执行具体操作，工作流负责报告、预览和版本发布。这种分工让每次修改都有明确依据和可检查的结果。

## 1. 它能做什么

当前已经实现的编辑操作是**段落对齐**：对一个明确定位的段落，或一批已确认的正文段落，设置左对齐、居中、右对齐或两端对齐。编辑器会核对基础文件和目标身份，记录修改前后的直接对齐值，并在保存后重新读取验证。已经满足的操作单独标记，不把重复执行当作新的修改。

配套的结构索引能读取主文档段落，为每段保存版本内对象 ID、XML 路径、文本、样式标识、直接对齐值和角色判断依据。它能区分表格内段落、标题候选、正文候选及需要人工定位的复杂内容；普通 `Normal` 样式只作为正文候选，不足以自动证明该段属于论文正文。当前正文批量编辑路径因此需要记录明确的范围确认，执行前还会重建计划和检查确认记录。

按已确认架构，编辑核心将逐步扩展到以下格式范围：

| 对象 | 建设目标 |
| --- | --- |
| 页面与分节 | 纸张、方向、页边距等明确属性 |
| 标题与正文 | 字体、字号、字形、对齐、缩进、段前段后间距和行距 |
| 已有脚注、尾注和引用 | 调整外观，保留原有文字及引用信息 |
| 目录与页码 | 调整样式和字段；在标题映射可靠时转换手工目录，并独立刷新与验证 |
| 表格 | 调整表格、单元格和表内文字的格式，保留数据 |

这些项目是后续能力目标，不能据此认为当前编辑器已经全部支持。首版边界也不包含论文润色、论点修改、参考文献内容生成或条目重排，以及图片尺寸和位置调整。

## 2. 如何实现

编辑核心采用 **C#、.NET 10 和 Open XML SDK**，作为独立程序由 Python 工作流调用。DOCX 包内的正文和格式以结构化部件保存，编辑器通过 SDK 定位对象并修改指定属性。以当前“将一个段落居中”为例，程序设置该段落的对齐属性，不重新生成段落文字，也不重建整篇论文。

一次编辑主要经过以下步骤：

1. **建立索引并核对版本。** 读取论文结构，计算文件哈希，确认输入仍是用户选定的父版本。对象 ID 仅在对应版本中有效，不能直接套到另一份文档。
2. **接收类型化操作。** JSON manifest 明确记录规则 ID、目标 ID、属性、目标值、实际范围，以及基础文件和目标文本哈希。批量操作还记录目标 XML 路径与预期的修改前值。编辑器不解析用户原话；规则依据和用户决定由上游可信工作流核对。
3. **检查可执行条件。** 拒绝未知属性、无效值、过期版本、变化的目标和不安全的定位。段落对齐必须声明实际作用于整个段落，不能把它伪装成只改几个选中文字。新解析规则中的局部范围也不能被旧规划器忽略后扩大到全部正文。
4. **在暂存副本上修改。** 原文件只读，输出文件与输入分开；只修改命中的属性。当前批量编辑把所有操作写入同一暂存副本，任一目标或整体校验失败都不发布该批次结果，已有输出也不会被覆盖。
5. **重新读取并验证。** 当前实现检查 Open XML 结构、主文档段落文本、目标对齐值及主文档之外的各个包部件；批量编辑还核对未命中段落的对齐值。验证通过后才发布新文件，并返回输出哈希和逐项前后值。

Python 工作流再核对编辑器结果与文件哈希，调用独立预览器生成可选中文字的 PDF，构建 JSON／Markdown 报告，并交给版本存储发布。每次实际修改创建选定父版本的新子版本，V0 和已发布历史版本保持只读。没有实际变化的后续操作不生成冗余 DOCX 版本。

完整架构还要求处理样式继承、直接格式覆盖和操作依赖：同类内容优先使用适当样式，避免修改共用样式时波及非目标对象；局部例外采用局部操作；验证要读取实际生效值。这部分仍需继续开发，当前段落对齐编辑器只处理直接属性，不解析继承样式。

目录页码刷新和页面预览由独立组件承担。写入格式属性或通过 XML 结构校验，并不能证明分页、目录页码和 Word 显示已经正确。字段刷新要在临时副本上执行并复核；当前编辑器尚未实现字段刷新，不能把预览转换成功当作下载 DOCX 的字段也已更新。

## 3. 相比使用 LLM 处理文档的优势

对于让 LLM 自由决定修改动作或重新生成文档的方案，AutoFormat 将执行限定为已知、可验证的操作，主要获得以下优势：

| 方面 | 确定性编辑核心的优势 |
| --- | --- |
| 内容保护 | 针对格式属性修改，并比较修改前后的文字与其他部件，降低无意改写正文、引用或表格数据的风险 |
| 范围控制 | 目标 ID、文本哈希、XML 路径和实际范围共同约束操作；定位不可靠时停止，避免把局部要求扩大 |
| 结果验证 | 从输出文件重新读取属性并比较目标值，区分已满足、修改通过和失败，成功结论有程序证据 |
| 可重复与可测试 | 已知操作采用固定处理逻辑，可为版本过期、目标变化、幂等性和内容保护建立回归检查 |
| 成本与隐私 | 已知格式操作不需要逐次调用模型，也不需要将论文全文发给云端模型；新增修改可只处理受影响对象 |
| 追溯与恢复 | 操作关联规则、版本、前后值和校验结果，失败时保留父版本，便于定位问题及从历史版本继续修改 |

例如用户只要求把某段改成居中，编辑器会执行对齐操作并验证该值，而不会同时推测字号、调整其他段落或润色文字。学校要求不明确、模板未确认或规则冲突时，上游工作流保留待定状态，编辑器不会凭常见论文格式自行补全。

这些收益来自受控操作、明确范围、验证和版本保护，并不意味着程序没有缺陷，也不意味着 LLM 无法参与文档处理。LLM 可以用于 Brief 语义理解；若一个 LLM 方案同样通过类型化操作调用确定性编辑器，并采用同等校验，也能获得这些保障。AutoFormat 的选择是将语义理解与实际文件修改分别管理，限制模型推断直接影响论文文件的机会。

目前尚无与 LLM 文档处理方案的同条件基准测试，不能宣称具体的速度提升、成本下降比例或零误改。

## 4. 与 AutoFormat 工作流的配合及当前进度

按产品架构，用户首次只需上传学校 Brief 和论文 DOCX。Brief Parsing 输出规则与证据，结构扫描和规划环节筛选定位可靠、无冲突且受支持的规则，编辑核心在副本上执行并校验，工作流发布 V1、报告和预览。未确定项留到 V1 发布后的问题队列；后续回答和预览微调只重新规划受影响对象及依赖，不覆盖原稿或历史版本。

当前已具备段落索引、单段与批量对齐编辑，以及确认后的对齐操作到报告、预览和版本发布的连接。该正文范围确认路径用于当前较窄的后续编辑能力，不是首次生成 V1 的输入要求。首次发布器目前仍复制 V0 作为 V1 基线，并报告尚未执行的规则；可靠的首次自动规划和更广的编辑操作仍待完成。因此，“生成了 V1”不能视为“已经自动解决绝大部分格式问题”。
