# 预览与用户编辑第六步：实际编辑、验证与新版本发布

日期：2026-10-08。接续[第五步规则冲突与快照](preview-feedback-rules-step5.md)。

本步把已核对的反馈规则接入 DOCX 编辑核心。配置了编辑器和渲染器的宿主中，清晰、定位可靠且无冲突的反馈提交后自动生成新版本；缺值、定位不唯一、扩大范围或冲突先显示确认选项，确认完成后继续执行。每次实际修改都从选定父版本复制，生成独立 DOCX、JSON／Markdown 报告和可选中文字的 PDF，原稿和历史版本保持不变。

## 1. 本步实现

- 字符级字体、字号和字形修改；段落对齐、缩进、间距等已注册属性；可靠表格的边框；明确分节的页面属性。实际范围来自服务端复核后的对象和字符片段，不从 PDF 坐标直接编辑。
- 选区落在一个 Word run 中间时按 UTF-16 边界拆分，保留原 run 属性及空白，不拆开代理对。中文／拉丁字符过滤按 Unicode 字符判断，混合文字不会被整段套用一种字体。
- 计划、执行、Open XML 校验、受保护内容比较、保存后有效属性回读、PDF 渲染和原子发布。任何目标不安全、物理属性冲突、校验失败或预览失败，都不替换当前版本。
- 本处例外和已确认反馈随当前分支继承；新全局规则再次检查例外。后续编辑保留父版本累计修改和原始用户决定。
- 前端显示执行进度、失败原因和重试入口；成功后载入新版本预览与下载链接，旧选区作废。宿主未配置编辑能力时仍可查看预览和核对规则。

## 2. 契约与执行边界

新增严格版本化契约 `FeedbackExecutionRequest/1.0`、`FeedbackExecution/1.0`、`FeedbackEditManifest/1.0` 和 `feedback-edit-result/1.0`，Schema 同步导出到公共契约目录和 API 包。请求必须绑定任务、父版本、DOCX 哈希、预览上下文和期望规则快照；客户端不能直接提交编辑操作。

新规则快照使用 `FeedbackRuleSnapshot/1.2`、编译器 `feedback-rules/1.2` 和 `FeedbackRulesReview/1.1`，旧 1.1 快照和 1.0 核对契约保持原语义。反馈发布沿用独立 `VersionNode/1.1` 引用，原 1.0 版本节点形状不变。

Python 在计划和执行前重放反馈原话、目标确认、范围决定、冲突决定及所选版本学术依据，再产生仅含注册属性和值的 manifest。C# 的 `plan-feedback`／`apply-feedback` 只处理该类型化输入；不理解或执行用户原话，也不调用模型。编辑器及相关 DLL、索引工具和 PDF.js 资源均须通过固定哈希检查。

编辑结果须覆盖全部已验证片段，并逐条匹配规则、对象、属性和目标值。反馈路径不接受只完成一部分的候选文件。字体范围、字段、修订、隐藏内容及不可靠结构仍受到编辑器安全检查。

## 3. 跨版本继承与审计

从父快照继承时，服务端读取父版本与新版本的真实 DOCX 索引，检查发布哈希及对象数量，并建立 `(part, XML path, kind)` 的一一映射。段落文本、story 和可编辑性必须一致；不能证明时转为待确认。继承不复用旧 PDF 页码或坐标。

继承保留已裁剪的学术规则片段与反馈片段，因此本处例外不会在下一轮被全局基线覆盖。新版本只继承其实际父版本的发布依据，不继承未发布核对头或其他分支的决定。

版本报告追加每个已验证片段的前值、目标值、实际操作和快照引用，保留反馈原话、目标选择、范围确认及冲突选择的原始回答。历史报告、累计修改和旧决定按父版本保留。

## 4. 幂等、恢复与原子发布

执行阶段为 `planning → editing → validating → rendering → validating → ready`；失败返回 `failed`，已经满足目标格式返回 `no_document_change`。状态和计划／结果证明持久化在 SQLite 中。

- 相同请求 ID 和相同内容返回同一执行结果；不同内容复用请求 ID 会被拒绝。不同进程同时提交同一请求，只能由一个执行尝试发布。
- 每次阶段更新续期 600 秒租约。失败可使用原请求重试；进程中断且租约过期后可重新取得执行权。
- 发布事务再次检查当前工作版本、规则核对头、反馈与决定前缀、父预览及执行尝试。编辑或渲染期间改答会阻止旧结果发布。
- 若发布成功后回执写入或网络响应中断，查询执行状态会从已发布版本恢复成功结果，不重复生成版本。
- 格式已满足时保留原始 DOCX 字节并保存执行证明，不渲染、不创建冗余 DOCX 版本。选区拆分只在内存中用于回读核对。

临时副本与渲染产物在项目版本库的独立 `.operations` 工作目录内产生，成功或失败后清理。只有所有产物通过检查后，版本、报告、预览和工作起点才一同发布。

## 5. API 与本地宿主

所有数据路由继续要求回环访问、会话凭据和同源检查。

| 路由 | 用途 |
| --- | --- |
| `GET /api/tasks/{task}/feedback-execution-capability` | 查询当前宿主是否配置实际编辑能力 |
| `POST /api/tasks/{task}/versions/{version}/feedback-executions` | 提交绑定就绪快照的执行请求 |
| `GET /api/tasks/{task}/feedback-executions/{request}` | 查询进度、恢复已发布结果或取得失败回执 |

原反馈接收、定位、分析和规则核对接口的职责保持独立；自动流程由界面在这些步骤确认完成后调用执行接口。

`autoformat.preview_host` 在[第二步启动参数](preview-ui-step2.md)基础上增加以下四个参数，必须同时提供：

```text
--editor-sha256 <编辑器 DLL 的 SHA-256>
--soffice <明确的 soffice.com 路径>
--soffice-sha256 <soffice.com 的 SHA-256>
--font-fingerprint <当前字体环境标识>
```

宿主复用可信索引配置中的 .NET 和编辑器路径，启动前检查配置；不自动安装运行时、字体或 LibreOffice。不提供上述参数时继续运行预览与核对模式。

## 6. 当前限制

当前执行入口要求**整轮规则快照为 ready**。快照中只要仍有待确认、待定位、未解决冲突或不支持片段，就不会执行该轮，包括与这些片段独立的可靠规则。这比架构要求的“只暂停受影响操作”更保守；后续需要增加可独立重放和发布的执行投影，不能通过删除 ready 校验或把待定片段标记为已验证来放行。

通用反馈执行暂不覆盖目录／页码缓存刷新、题注位置等依赖额外能力的操作；这些要求继续明确阻断或保留待处理。PDF 预览成功不等于 Word 分页一致，也不等于字段缓存已刷新。

第七步继续完善问题与历史版本的产品操作，第八步进行整体集成与打包验收。本步不改动 Brief Parsing 来源项目。
