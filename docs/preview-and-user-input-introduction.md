预览与用户输入模块连接论文处理结果和用户的后续决定。它的目标是让用户查看某个版本的论文、了解修改结果和未处理事项，并通过回答问题或选中文字提出格式微调需求。模块将反馈关联到明确的文档版本、位置和作用范围，再交给规则校验及编辑工作流处理。

按已确认流程，用户首次只需上传学校 Brief 和论文原稿 DOCX。系统先处理可靠规则并发布 V1，随后才开放剩余问题和预览微调；选区、修改提示和逐项回答都不是首次生成 V1 的前置输入。当前首次发布器仍生成原稿副本基线，完整自动格式修改能力尚待完善。

## 1. 它负责什么

模块包含两类相互配合的入口。

**预览与选区入口**用于查看已发布的论文版本。用户用光标选择文字，输入例如“这一段改为居中”的需求，并明确选择修改范围。按架构，范围可为仅选中处、所在段落、所有同类内容或全文；默认从选中处开始，提交前展示实际作用范围。首版采用文字选择，不提供圈画批改。

**问题与决定入口**用于处理系统无法确定的事项。界面应展示相关 Brief 原文、候选解释、受影响位置和选择的后果，允许用户回答、跳过或暂缓。V1 发布后先处理冲突及来源不一致，再按类别询问是否沿用 Brief 自带模板中未明确规定的版式。跳过或暂缓不等于同意默认值。

用户还可以下载当前 DOCX 和报告、查看历史版本，或选择某个旧版本作为继续修改的起点。报告说明实际完成的操作；预览帮助检查页面呈现，两者共同支持后续决定。

## 2. 预览如何生成

当前后端通过可替换的 `PreviewRenderer` 接口接收已存储的 DOCX 和预览标识，使用 LibreOffice 无界面模式转换为 PDF。每次转换先复制输入到独立工作目录，使用单独的 LibreOffice 配置，设置执行时间及输出资源限制，并检查源 DOCX 在转换前后保持不变。

只有生成的 PDF 可读取、至少有一页并包含可提取文字时，后端才发布预览。预览元数据记录源 DOCX 哈希、PDF 哈希、页数、可提取文字数量、渲染器名称和版本，用于后续核对文件身份。当前渲染前检查也会拒绝嵌入对象、外部关系和外部内容字段等尚未获支持的文件内容。

前端按架构将使用 PDF.js 的文字层显示并选取文字，因此预览需要保留文字信息。完整 PDF.js 界面目前尚未实现；已有后端可生成带文字的 PDF，不能据此声称用户界面的选择与提交流程已经完成。

PDF 是查看和定位的辅助文件，后续实际编辑仍针对 DOCX。LibreOffice 与 Word 可能存在字体、分页和位置差异，预览不承诺与 Word 完全一致。PDF 转换成功也不能证明下载 DOCX 的目录或页码字段已经刷新，字段刷新须单独验证。

## 3. 如何把选中文字定位到论文

界面中的页码或坐标不能直接确定要修改哪个 DOCX 对象。用户反馈需要携带基础版本、预览标识、所选文字、前后文，以及 PDF 页和文字层跨度等定位提示；服务端从可信存储读取实际文件及绑定元数据，再进行检查。

当前已有两层只读定位能力：

1. **Python 核对 PDF 证据。** 检查源 DOCX 与 PDF 的哈希、预览页数，以及选中文字是否在所声明页面中恰好出现一次。文件不匹配、文字不存在或重复时暂停。
2. **C# 核对 DOCX 目标。** 在对应版本的主文档段落索引中查找精确文字，再检查前后文和段落结构。只有唯一、安全的匹配才能产生 `SelectionAnchor`，记录 DOCX 对象 ID、XML 路径和字符跨度。

当前定位原型采用保守策略：文字在主文档中重复时，即使提供上下文也不会自动选定其中一处；含换行的选区、隐藏文字、修订、字段或绘图等复杂目标同样暂停。页眉页脚、脚注尾注不在当前索引范围内。PDF.js 文字层偏移尚不能独立验证，只作为提示保留。

选区锚点证明“位置在哪里”，后续仍需确定“要改什么”和“实际改多大范围”。旧版本或旧预览的选区也不能直接应用到新 DOCX；按架构需要重新定位并向用户说明差异。

## 4. 用户输入如何进入编辑流程

按已确认架构，自由文本反馈通过轻量入口解析，复用论文格式规则模型，不重新运行整份 Brief 的提取、审计和条件解析流水线。首版计划用受控词典和句式理解常见表达，识别不了的部分展示缺失字段，让用户补充。论文正文和选中文字默认不发送给模型。

反馈需要区分以下情况：

| 类型 | 处理方式 |
| --- | --- |
| 已有规则未正确执行 | 引用原规则和验证结果，核对实际属性后处理 |
| 新的格式要求 | 转换为明确的对象、属性、值和范围，再校验 |
| 表达、目标或范围不清 | 保留已理解信息，询问缺失部分 |
| 咨询或范围外请求 | 作相应回应，不凭此产生格式操作 |

例如用户说“这里还是宋体”，系统应先核对该处原本应遵守什么规则；用户说“这一段居中”，实际修改单位是整个段落，界面应明确显示这一点。如果输入写“所有二级标题”，而范围控件仍为“仅选中处”，系统须请用户统一两者，不能静默改变范围。

表达清晰、定位可靠且无冲突的受支持需求可进入执行；定位不唯一、范围扩大或与已确认规则冲突时，先取得明确决定。冲突时按架构提供保留原规则、本处例外或更新规则等选择。编辑核心只接收通过校验或由用户明确确认的类型化规则，不直接执行原始输入文字。

当前完整自由文本反馈解析与上述冲突、例外交互仍待开发。已有后端支持用户决策的追加记录，以及较窄的正文范围确认和对齐执行 API，不能等同于通用预览反馈入口已经完成。

## 5. 输入、输出与版本配合

| 环节 | 主要输入 | 主要输出 |
| --- | --- | --- |
| 当前预览后端 | 已存储 DOCX、预览标识、渲染配置 | PDF 和预览元数据 |
| 当前选区定位原型 | 选中文字、上下文、版本／预览提示，以及服务端可信绑定 | 唯一安全锚点，或过期／歧义等状态 |
| 按架构建设的反馈入口 | 用户原话、选区、基础版本和范围选择 | 类型化候选规则、缺失信息或待用户决定事项 |
| 编辑与版本工作流 | 校验后的规则、明确目标、选定父版本 | 新 DOCX、对应报告、预览和版本记录 |

每条反馈保留其原话、选区、依据版本和后续决定。成功编辑后生成新版本及新预览，下一轮使用新预览；V0 与历史文件不被覆盖。从旧版本继续修改会创建新的分支，不删除已有后代。只有咨询、跳过或暂缓而没有文档修改时，保留决定记录，不生成冗余 DOCX 版本。

这种设计将用户看到的位置、希望修改的属性和授权范围关联起来，也让后续报告能够说明为什么修改、修改了哪里以及哪些事项仍未处理。预览器保持独立接口，未来可替换为更高精度的实现。

当前已实现 DOCX 转 PDF、预览元数据及文字存在检查、PDF 选区证据核对、DOCX 唯一文字锚点、版本与决策存储，以及确认后对齐编辑的报告和预览发布。完整前端、文字层跨度验证、自由文本反馈、冲突与例外处理，以及更广的对象定位和编辑仍需继续建设。
