# AutoFormat 的 Brief Parsing 模块介绍

> 依据当前项目架构与实现整理，日期：2026-10-04。

Brief Parsing 是 AutoFormat 中负责理解学校格式说明的模块。它读取学校提供的 Brief 或模板，把分散在段落、表格和说明中的格式要求整理成带原文证据、适用对象和处理状态的结构化规则，供后续格式编辑器使用。模块关注字体、字号、对齐、行距、缩进、页边距、目录、页码和表格等格式要求；字数、篇幅、文献数量及论文应写什么等内容要求不进入解析和问题队列。

AutoFormat 在项目内复用既有 Brief Parsing 流水线，并扩展论文格式领域包、规则词典和输出契约。这里的“专用模块”是对解析流程和执行边界的专门设计，不意味着重新训练一个大模型，也不意味着从零重写全部解析能力。

## 1. 如何提高识别准确性和处理效率

模块采用程序处理与 LLM 理解相结合的方式。程序先安全读取文件，保留段落、标题、列表、表格及可读取的页眉页脚、脚注等结构，再切分条款，建立能回到精确原文的证据索引。模型围绕这些条款提取候选要求，后续由程序归一和校验，减少因整篇文档上下文混杂而产生的误判。

在论文格式识别上，模块做了以下工作：

- **区分要求与示例。** 将明确格式说明、示例、背景、模板观察、范围外内容和来源不明片段分别标记，避免把示例论文的内容或模板当前外观当成学校明文要求。
- **使用论文领域词典。** 对中文字号、常见字体、单位和目标角色采用受控规则。例如保留“小三号”的原文，同时规范化为 15 pt；区分正文、不同级别标题、目录条目，以及拉丁字母和数字的字符范围。
- **拆分复合要求并保留上下文。** “一级标题居中、小三号、黑体加粗”拆成对齐、字号、字体和加粗四项规则。相邻格式条款可继承同段中明确的目标，同时保留目标和值的证据；相同规则合并后仍保存各处来源。
- **检查遗漏。** 通用覆盖审计检查条款是否得到处理，论文来源审计进一步逐个格式属性核对。即使一句话已经提取出字体，未覆盖的段前间距仍会单独报告；疑似漏提、不支持、已识别待定、来源不明和读取盲区分别呈现。
- **转换模型候选。** 候选须与程序从原文取得的对象、属性、值、单位和范围证明一致；通过后保留模型 Requirement ID，重复候选共享规则，未通过的候选记录原因。候选遗漏的章节或提交限制仍由原文证明保留。受控中英文表达已扩充，见 [开发记录](brief-parsing-expression-candidates.md)。

效率方面，模块在模型调用前筛除示例、背景和范围外片段，按条款分块发送需要理解的内容，并在模型输出端再次过滤。例如“摘要不少于300字，字体宋体”仅保留字体要求。常见明确格式值由确定性程序提取和换算，不再让模型决定其规范值；通用冲突解析阶段只在存在冲突时触发。并发上限、任务超时、有限重试和 Token 预算控制调用资源，阶段耗时与用量记录便于后续优化。

这些措施用于减少误识别、遗漏和无关模型处理。目前尚无经确认的真实 Brief 标注评测支持具体准确率或提速比例；条款覆盖率、格式线索计数和回归测试通过数也不能替代这类指标。

## 2. 如何应对 LLM 幻觉

模块把 LLM 输出作为待验证候选，能否成为可信规则由证据和程序校验决定。

首先，候选必须引用本次输入中真实存在的证据 ID。程序检查引用范围、原文跨度和哈希，并核对数值、单位及约束表达；结构化 Schema 检查字段和类型。未知引用、无效结构或无法验证的模型结果不会混入已接受的需求，失败与不完整状态会保留在诊断中。

其次，当前自动论文格式提取只在已知目标、明确的单一值和精确原文依据均可建立时输出 `verified` 规则。Brief 只写“正文格式”而没有给出字号时，模块不会补成“小四”；模板呈现某种版式，也不会因此产生学校强制规则。缺值、冲突、目标歧义和未支持表达保留为待处理项。保存的解析 Bundle 还会从同一份需求 IR 重算格式规则和来源审计，防止规则值或证据链接被改动后仍通过校验。

此外，Brief 被作为不可信数据与系统指令分开传递，模型调用不开放文件编辑或工具执行权限，降低文档中夹带指令影响流程的风险。后续编辑器还要独立核对支持能力、论文目标定位、适用条件和冲突，才能执行规则。LLM 不直接修改论文。

这些措施不能保证模型永远不出错，但能限制错误候选进入自动编辑链路。无法确认的项目明确展示依据和原因，由后续复核或用户决定补足。

## 3. 为什么采用专用模块，而不直接交给通用 agent

AutoFormat 需要长期重复完成一个边界明确的任务：把学校说明转成可追溯、可校验、可交给编辑器执行的格式规则。仅让类似 Codex 的通用 agent 阅读文件并自主完成任务，仍需要额外建立证据索引、来源分类、格式词典、冲突策略、稳定输出契约和回归评测，才能满足这些产品要求。

专用模块将这些要求固化为可复用的程序能力：每条规则采用统一的数据结构和状态，能回到原文；常见格式值按版本化词典解释；不确定项有明确去向；解析模型可以通过适配器替换，而后续编辑器继续使用相同契约。调用范围、预算和失败行为也更容易控制，便于定位问题和维护历史结果。

通用 agent 可以辅助开发解析器、扩展词典、分析失败样本和编写测试。专用模块承担产品运行时的规则解析与校验，两者能够配合。选择专用模块的理由是 AutoFormat 对稳定接口、证据追溯和自动编辑边界的要求，而非预设通用 agent 没有理解这些文档的能力。

## 4. 输入、输出与后续工作流

模块本身的输入是学校 Brief／模板，当前支持 UTF-8 文本、DOCX 和具有文字层的 PDF，以及论文领域、任务标识等调用配置。旧版 `.doc` 和没有文字层的扫描 PDF 不在当前支持范围；OCR 仍属后续能力。用户在 AutoFormat 首次上传的另一份文件——论文原稿 DOCX——交给后续结构扫描和编辑环节，不作为 Brief 语义解析的输入。

当前论文入口 `BriefParserService.parse_academic` 输出版本化的 `AcademicParseBundle/1.6`，主要包括：

| 输出 | 用途 |
| --- | --- |
| `Requirement IR` 与证据索引 | 保存结构化需求、来源原文、定位、冲突和未解决项，作为解析事实源 |
| `AcademicFormatRuleSet/1.5` | 描述目标、属性、值、单位、对象／字符／章节范围、条件与约束，保留冲突交集和未受影响分片，供编辑器进一步评估 |
| `AcademicSourceReview/1.2` | 展示来源分类、疑似遗漏、待定项、不支持项和读取盲区 |
| `TemplateLayoutReport/1.1` | 保存 Brief 自带 DOCX 的版式、样式／主题继承和位置，按范围与明文对照；观察值待确认 |
| `AcademicDecisionSnapshot/1.0` | V1 后的回答生成独立新快照，保留有效规则、完整范围、冲突、剩余问题与决定历史；不改写原始 Bundle |
| Manifest、诊断与 Markdown 呈现 | 记录来源和处理版本、完整性状态、阶段信息，并提供可阅读的解析报告 |

按已确认的工作流，解析结果会由 AutoFormat 内部直接传递，用户无需导出再导入 JSON。后续结构扫描器定位论文对象，规划器核对规则证据、适用条件、冲突、编辑能力和目标位置，确定性编辑器在 V0 的副本上执行可靠规则，验证后发布 V1、对应报告和可选中文字的预览。`verified` 表示解析侧规则通过校验，仍需后续定位与执行检查，并不等于论文已被修改。

首次处理只需上传 Brief 和论文 DOCX。局部未确定项保留在 V1 报告和后续问题队列，不阻断其他独立可靠规则；解析整体失败则停止格式编辑并给出诊断。V1 发布后先处理冲突，再按类别确认是否沿用 Brief 自带模板中未明确规定的版式。用户查看预览后还可选中文字提出微调需求；按架构，此类反馈通过轻量解析入口处理，只重新规划受影响对象及依赖。每次实际编辑从选定父版本创建新 DOCX、报告与预览，V0 和已发布历史版本保持只读。

当前已实现论文领域包、常见明确格式提取、来源分类、范围过滤、类型化规则、来源审计、模板样式／主题读取、范围冲突分析与解析决策闭环。V1 后可通过 API 确认条件、选择冲突规则、确认模板、补充格式值或跳过／暂缓；修订保留历史并使不再适用的旧答案失效。复杂布尔条件、完整视觉区域、自由文本回答解析、产品问答界面和 OCR 尚待扩展；自动规则规划及更广的 DOCX 编辑能力也尚未完成，当前 V1 发布链路仍以原稿副本为基线。上述端到端流程是已确认的产品架构，不代表现阶段已能自动完成全部格式修改。详见 [规则语义开发记录](brief-parsing-rule-semantics.md) 和 [决策闭环开发记录](brief-parsing-decision-loop.md)。
